💡 Step Back 02

Instant vs. Time-Taking Instructions

Up to now, we’ve been telling the computer to do things. But not all things finish in the same amount of time.

⚡ Instructions that finish instantly (synchronous)

int a = 5 + 3; // done immediately String name = "Ayaan".toUpperCase(); // done immediately List<int> doubled = [1,2,3].map((n) => n * 2).toList(); print(a);

Each line runs, finishes, and the next line begins. The CPU does the work right now and gives you the answer right now.

⏳ Instructions that take time (asynchronous)

// These can take milliseconds, seconds, or even minutes: // • Download a JSON from a server // • Read a large file from disk // • Query a database // • Wait for user to pick a photo // • Wait 3 seconds with a timer // The CPU isn't doing the work — it's waiting for // the network, disk, or another device to respond.

If we wrote async work like sync code, the program would just freeze during the grey “waiting” part — the UI would hang, no button would respond, nothing else could run. We need a way to say “start this, but don’t block me — let me know when it’s done.”

🔮 Concept 03

Enter: Future<T>

A Future is Dart’s way of saying: “I don’t have the value yet, but I promise I’ll have one — a T — at some point.”

🎫 Analogy: You hand in your jacket at a cloakroom and get a numbered ticket. The ticket is not your jacket — but it’s a promise that when you show it later, you’ll get your jacket back. Or, if something went wrong, you’ll get bad news. A Future<Jacket> is that ticket.

🎭 The three states of a Future

⏳
Pending
Work in progress
✅

💥

Every Future starts pending. Eventually it either completes with a value, or fails with an error. Your job as the programmer is to say what should happen in each case.

🧪 Creating a Future you can experiment with

// Future.delayed runs some code after a delay — great for practice Future<String> fetchUsername() { return Future.delayed( Duration(seconds: 2), () => "Ayaan", // this becomes the Future's value ); } // Type tells you what will eventually arrive Future<String> name = fetchUsername(); // eventually a String Future<int> score = fetchScore(); // eventually an int Future<void> saved = saveToDisk(); // eventually just "done"
📜 The old way 04

Using a Future: .then & .catchError

The first tool Dart gives you is “callback style.” You tell the Future: when you’re ready, run this code on the value.

📐 Attaching a callback with .then()

Future<String> fetchUsername() => Future.delayed(Duration(seconds: 2), () => "Ayaan"); void main() { print("1. asking for username…"); fetchUsername().then((name) { print("3. got: $name"); }); print("2. main() keeps going — not blocked!"); } // Output order: // 1. asking for username… // 2. main() keeps going — not blocked! // 3. got: Ayaan (← 2 seconds later)

Notice print("2. …") runs before the result arrives. That’s the whole point — the program didn’t freeze.

💥 Handling errors with .catchError()

Future<String> fetchUsername() => Future.delayed( Duration(seconds: 1), () => throw Exception("network down"), ); void main() { fetchUsername() .then((name) => print("got $name")) .catchError((err) => print("failed: $err")); } // failed: Exception: network down

If the Future errors, .then is skipped and .catchError runs instead.

📞 Think of .then as “call me back”. You hand the Future a phone number (a function). When the result is ready, it dials you. You’re not sitting by the phone — you’re off doing other things.
😰 Motivation 05

“But I can do that with a callback…”

A fair question: if .then works, why do we need anything else? Because real programs have several async steps in a row — and callbacks get ugly fast.

🎯 A realistic scenario

Log in a user, then load their profile, then load their posts, then show it on screen. Each step depends on the previous one — and each one is async.

❌ With .then — nested callbacks
login(email, password).then((userId) { loadProfile(userId).then((profile) { loadPosts(profile.id).then((posts) { render(profile, posts); }).catchError((e) => print("posts failed: $e")); }).catchError((e) => print("profile failed: $e")); }).catchError((e) => print("login failed: $e"));

Each step nests inside the previous one. The code drifts to the right. Error handling is duplicated. It’s called callback hell or the pyramid of doom for a reason.

✅ With async / await — same logic, flat
try { var userId = await login(email, password); var profile = await loadProfile(userId); var posts = await loadPosts(profile.id); render(profile, posts); } on Exception catch (e) { print("something failed: $e"); }

Reads top-to-bottom, like a regular function. One try / catch handles every step. That’s the whole motivation for async / await.

✨ The new way 06

async / await

Two keywords, one promise: write async code that looks synchronous. It’s not magic — it’s just a cleaner way to talk to the same old Future.

🔑 Two keywords — that’s the whole feature

// 1. Mark a function as "async" → it now returns a Future Future<String> greet() async { // 2. Use "await" inside to pause until a Future completes String name = await fetchUsername(); return "Hello, $name!"; }

async

Marks a function. Its return type must be Future<T>. Lets you use await inside.

await

“Pause here until this Future completes, then give me the value.” Only works inside an async function.

🔄 Same code, two styles

With .then

Future<void> showUser() { return fetchUsername().then((name) { print("Hello, $name!"); }); }

With async / await

Future<void> showUser() async { String name = await fetchUsername(); print("Hello, $name!"); }

Both do exactly the same thing. The second one just reads like normal top-to-bottom code. No indentation pyramid, no callback, no lambda.

⏸️ Mental model: await is a pause button for your function only. The rest of the program keeps running — other UI events, other timers, other futures — but this function freezes right there until its value arrives. Then it resumes from the next line.
🛡️ Errors 07

Errors: .catchError vs try / catch

A common student question: “We already know try / catch — why does async code need a whole other thing (.catchError)?” Great question. The answer is: it doesn’t — once you use await.

🤔 The problem with plain try/catch around a Future

Looks right — doesn’t work

void main() { try { fetchUsername(); // returns a Future — doesn't throw here! } catch (e) { print("caught: $e"); // ❌ never runs } } // Uncaught exception: network down

The call fetchUsername() returns a Future immediately and the try block finishes successfully. The error happens later, on a different tick — long after we’ve left the try. So catch never sees it.

That’s why .catchError exists. The error has to be attached to the Future itself, not to a block of synchronous code:

fetchUsername() .then((name) => print("got $name")) .catchError((e) => print("caught: $e")); // ✅ works

🎉 But await brings regular try/catch back

When you await a Future, Dart effectively unwraps it. If it completes with a value, you get the value. If it completes with an error, it’s thrown right there in your function — which means a normal try / catch can catch it.

try / catch works again

Future<void> main() async { try { String name = await fetchUsername(); print("got $name"); } on SocketException catch (e) { print("network issue: $e"); } catch (e) { print("something else: $e"); } finally { print("always runs — hide spinner"); } }

Now the async code uses the same error-handling tools as synchronous code. You can even have multiple on ExceptionType catch clauses and a finally block — just like normal.

⚖️ Compare 08

Full Comparison, Line for Line

Same task four different ways. Read them top to bottom and feel the difference yourself.

🎯 Task: log in, load profile, show it. Handle any failure.

Attempt #1 — sync try/catch around a Future (BROKEN)

void showUser() { try { var id = login(); // id is a Future, not the real id! var p = loadProfile(id); // ❌ passing a Future, not an int print(p.name); // ❌ p is a Future, has no .name } catch (e) { print("$e"); // ❌ never catches async errors anyway } }

This is what beginners try first. It fails in three ways at once — that’s why callbacks exist.

Attempt #2 — .then / .catchError (works, but ugly)

void showUser() { login() .then((id) { return loadProfile(id).then((profile) { print(profile.name); }); }) .catchError((e) { print("failed: $e"); }); }

It works. It’s also nested, hard to follow, and error handling feels tacked on.

Attempt #3 — async / await with try/catch (clean)

Future<void> showUser() async { try { var id = await login(); var profile = await loadProfile(id); print(profile.name); } catch (e) { print("failed: $e"); } }

Reads like a story. Same tools you already know (try, catch, finally) now work for async code too. This is the style you’ll use 95% of the time in Flutter.

🌊 Streams 10

Stream — Many Values Over Time

A Future delivers one value eventually. But what if values keep arriving — every few seconds, every key press, every message from a chat server? You need a Stream.

📻 Analogy: A Future is like ordering a pizza — you get one thing, then you’re done. A Stream is like tuning into a radio station — it keeps emitting sound until you turn it off (or the station stops broadcasting).
🌊 Streams 11

Consuming a Stream

Two main ways to react to each value a stream delivers: .listen() (callback style) and await for (async style).

📞 Callback style — .listen()

Stream<int> ticks = Stream.periodic( Duration(seconds: 1), (count) => count, ).take(5); // only the first 5 values, then stop ticks.listen( (value) => print("got: $value"), // onData — each value onError: (e) => print("oops: $e"), // any error onDone: () => print("stream finished"), // when closed ); // Output (one per second): // got: 0 → got: 1 → got: 2 → got: 3 → got: 4 → stream finished

🔁 Async style — await for

Future<void> printTicks() async { Stream<int> ticks = Stream.periodic( Duration(seconds: 1), (c) => c, ).take(5); try { await for (int value in ticks) { print("got: $value"); // runs for each value } print("stream finished"); // runs once at the end } catch (e) { print("oops: $e"); } }

It’s just a for loop — but instead of iterating over a List that already has all its items, it iterates over a Stream that delivers items over time. The loop body runs once per value as each arrives. And best of all, try / catch works around it.

🎧 Comparing the two: .listen() is “fire and forget” — hand in three callbacks, then move on. await for is “stay with me” — your function parks itself on the stream and processes each value sequentially. Use await for when the values must be handled one at a time; use .listen when you want to set up a reaction and let it run in the background.
⚡ Generators 12

Generators — sync* & yield

A generator is a function that produces a sequence of values on demand — pausing between each one. The magic keyword is yield.

🥟 Analogy: A chef who makes dumplings one at a time whenever a customer asks. She doesn’t cook 100 dumplings up front and store them in a giant pile — she waits, and when you say “another please” she pauses, makes one, hands it over, and waits again. A generator is a function that works exactly like that.

🔂 sync* produces an Iterable

// Marked sync* → returns Iterable<T> lazily Iterable<int> countTo(int n) sync* { for (int i = 1; i <= n; i++) { print(" (generator: about to yield $i)"); yield i; // "hand one value to the caller, then pause" } } void main() { print("before loop"); for (int v in countTo(3)) { print("main got: $v"); } } // before loop // (generator: about to yield 1) // main got: 1 // (generator: about to yield 2) // main got: 2 // (generator: about to yield 3) // main got: 3

Notice the interleaving. The generator doesn’t run to completion — it pauses at each yield, hands control back to main, and only resumes when the next value is asked for.

⚡ Generators 13

async* — Generators That Make a Stream

Same idea as sync*, but the values are produced asynchronously and delivered over a Stream. This is how you write your own custom streams.

🌊 async* produces a Stream

// Marked async* → returns Stream<T> Stream<int> countdown(int from) async* { for (int i = from; i >= 1; i--) { await Future.delayed(Duration(seconds: 1)); yield i; // push this value into the stream } } Future<void> main() async { await for (int i in countdown(3)) { print("tick $i"); } print("blast off!"); } // tick 3 ← after 1s // tick 2 ← after 2s // tick 1 ← after 3s // blast off!

🎯 The three “star” function shapes

MarkerReturnsProducesConsumed with
asyncFuture<T>One value, laterawait
sync*Iterable<T>Many values, lazily, synchronouslyfor (x in it)
async*Stream<T>Many values, over timeawait for / .listen

🔀 Bonus: yield* — delegate to another generator

Iterable<int> oneTwo() sync* { yield 1; yield 2; } Iterable<int> upToFour() sync* { yield* oneTwo(); // yields 1, then 2 from the other generator yield 3; yield 4; } print(upToFour().toList()); // [1, 2, 3, 4]

yield* means “yield everything from that other iterable/stream, in order.” Great for recursive or composed generators.

🛠️ Pattern 14

Putting It All Together

One realistic Flutter-style example that uses a Future, a Stream, and error handling together.

💬 A chat screen — fetch history, then watch for new messages

// Types from some imaginary chat library Future<List<Message>> loadHistory(String roomId); Stream<Message> liveMessages(String roomId); Future<void> openChat(String roomId) async { try { // 1. ONE Future — fetch the history we missed List<Message> history = await loadHistory(roomId); for (var m in history) renderMessage(m); // 2. STREAM — then subscribe to messages arriving live await for (Message m in liveMessages(roomId)) { renderMessage(m); if (m.text == "/bye") break; // stop listening } } on SocketException catch (e) { showBanner("you're offline"); } catch (e) { showBanner("error: $e"); } finally { hideSpinner(); // always runs — even if user exits chat } }

One function. One try / catch / finally. A Future and a Stream used back-to-back. This is the shape of most async code in real Flutter apps.

⚠️ Gotchas 15

Common Pitfalls

Four mistakes every beginner makes at least once. Spot them in your own code early.

① Forgetting await

Future<void> save() async { writeToDisk(); // ❌ forgot await — fires and forgets print("saved!"); // prints before the write is actually done } Future<void> saveCorrect() async { await writeToDisk(); // ✅ wait for the write first print("saved!"); }

② Sequential awaits when they could run in parallel

// ❌ Slow — each await waits for the previous to finish var user = await fetchUser(); // 1s var photos = await fetchPhotos(); // 1s → total 2s // ✅ Fast — start both, then await both together var results = await Future.wait([ fetchUser(), fetchPhotos(), ]); // → total 1s

Only chain awaits sequentially when later calls actually need the earlier result.

③ Using await without async

void main() { await fetch(); // ❌ compile error: not an async function } Future<void> main() async { await fetch(); // ✅ marked async → can use await }

④ Mixing .then and await for no reason

// ❌ Confusing — picks one style, then the other var user = await login().then((id) => loadUser(id)); // ✅ Stay in one style var id = await login(); var user = await loadUser(id);

Once you pick await, stick with it — don’t mix it with .then chains on the same Future.
